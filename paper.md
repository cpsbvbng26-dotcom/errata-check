# Summary

A scholarly artifact that carries a DOI is frozen: the PDF cannot be edited after
deposit. What can still be edited is the correction record — the errata file that
says which claims in the frozen artifact were wrong, which were withdrawn, and
which cannot be fixed. Because only one side of the pair can change, the two drift
apart. A quotation loses a character. An item is dropped from a count. An entry
declared unresolvable quietly becomes resolved.

`errata-check` audits the correction record against the frozen artifacts it
describes. The audit is declared in a TOML file: which passages the record claims
are printed, which it claims are absent, how many items it declares, which items
it has declared unresolvable, and the SHA-256 of each source. The tool extracts
text from the sources and reports each declaration as pass or fail.

**No inference is used.** There is no language model, no embedding, no fuzzy
matching — only presence, absence, and exact equality after a documented
normalisation of whitespace and character forms. The output therefore does not
need a human to re-check it, which is what allows the audit to run in continuous
integration on every push.

# Statement of need

Tools that check scholarly claims almost all act *before* publication, on the
manuscript: `statcheck` recomputes reported test statistics [@nuijten2016], the
GRIM test asks whether a reported mean is reachable from integer data
[@brown2017], and reference linters check that citations resolve. These operate on
the artifact that is still editable.

The correction record is the opposite case. It exists only *after* publication,
it is the one editable half of a frozen pair, and it is maintained by the same
author whose errors it lists. That last property is the reason a machine is
needed. Two of the tool's checks target it directly:

- **Completeness.** If the record says it lists twelve occurrences, twelve must be
  present. Under-counting is the cheapest way to shrink an admission.
- **Unresolvability.** An item declared unresolvable must not later appear as
  resolved without the declaration being changed first.

The remaining checks catch ordinary mistakes: altered quotations, a substituted
source file, a "last updated" date older than a date in the body, a count in prose
that disagrees with the count a command actually produces.

Because what can be settled deterministically from a printed page differs by
field, the tool also ships discipline-specific checks: recomputation of *p* from
printed test statistics and degrees of freedom (*t*, *F*, χ², *r*), the GRIM test,
check digits for ORCID, ISBN and ISSN, declared arithmetic relations between
printed numbers, Japanese era-year to Gregorian mapping for archival work, and
reference declarations that record which passage of a cited source supports which
claim — which also fails on a citation used in the body but missing from the
bibliography, and on a bibliography entry never used in the body.

# Testing

A checking tool cannot be trusted by passing, because a tool that inspects nothing
passes everything. `tests/check_tool.py` therefore builds a passing state and then
breaks it in 26 distinct ways — altering a quotation, declaring an absent passage
present, substituting a source PDF, removing a `sha256` declaration, falsifying a
count, rewriting an unresolvable item as resolved, and so on — asserting each time
that exactly the corresponding check fails. A final case asserts that a line
wrapped across a page boundary does *not* fail, so the suite also constrains false
positives. The suite reports 68 checks and requires no dependencies beyond `pypdf`
for PDF sources; the test PDFs are generated by `tests/make_pdf.py` so that a pass
cannot be an artefact of one particular real document.
